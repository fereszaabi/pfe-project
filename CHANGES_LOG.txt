================================================================================
  AFTER-SALES SERVICE WEBSITE — FULL CHANGES LOG
  Connecting the Laravel Backend to the React Frontend
  (Beginner-Friendly Explanation)
================================================================================

OVERVIEW
--------
The project has two separate parts:
  - BACKEND  → A Laravel (PHP) server that stores and manages all the data
               in a database. It runs at http://127.0.0.1:8000
  - FRONTEND → A React (JavaScript) app that users see in their browser.
               It was showing fake/hardcoded data instead of real data.

The goal of all these changes was to make the frontend talk to the backend
so that real data is shown, real accounts are created, and real actions
(like submitting a ticket) are saved to the database.

Think of the backend as a restaurant kitchen, and the frontend as the menu
and waitstaff. Before these changes, the menu was showing "pretend food"
that was never actually cooked. Now the waitstaff properly orders from
the kitchen and serves real food.

CHANGE 1 — NEW FILE: frontend/src/services/api.js
================================================================================

WHY:
  Every component (ClientDashboard, EmployeeDashboard, AdminDashboard) needs
  to send requests to the backend. Without a central place for this, each
  component would have to repeat the same code over and over (copy-paste),
  which makes it hard to maintain and easy to break.

  This file is like a "phone directory" — instead of every component looking
  up the backend's number themselves, they all call this one file which knows
  all the numbers.

WHAT WAS DONE:
  A new file was created at: frontend/src/services/api.js

  It contains:
  1. BASE URL — All API calls start with '/api', which Vite then forwards
     to the real backend at http://127.0.0.1:8000 (see Change 2).

  2. getToken() — Reads the login token from localStorage (the browser's
     built-in storage). When a user logs in, the backend gives them a
     secret token (like a wristband at an event). Every future request
     must include this token to prove who they are.

  3. authHeaders() — Builds the headers that go with every request.
     Headers are extra info sent alongside a request, like:
       - "Content-Type: application/json" → "I'm sending JSON data"
       - "Authorization: Bearer TOKEN"    → "Here is my wristband"

  4. apiRequest() — A reusable function to make any HTTP request
     (GET, POST, PATCH, DELETE). It handles errors automatically.

  5. apiUpload() — Same as above but for sending files (like images).
     Files need a different format called "multipart/form-data".

  6. Exported functions for every backend endpoint:
     - login(), register(), logout(), getMe()
     - getClientTickets(), createTicket()
     - getEmployeeTickets(), assignTicket(), updateEmployeeTicket()
     - getAdminDemandes(), getAdminStats(), createAdminUser()
     - updateClient(), updateDemandeStatus(), deleteUser(), takeMoney()

KEY CONCEPT — What is a token?
  When you log in, the backend confirms your identity and gives back a
  random string like "2|abc123xyz...". This is your token. You store it
  in localStorage and attach it to all future requests. The backend reads
  it and knows it's you without you having to log in again every time.

CHANGE 2 — MODIFIED: frontend/vite.config.js
================================================================================

WHY:
  The React app runs at http://localhost:5173 (in development).
  The Laravel backend runs at http://127.0.0.1:8000.
  These are different "origins" (different ports = different origins).

  When JavaScript in a browser tries to contact a different origin, browsers
  block it by default — this is called the "Same-Origin Policy" (a security
  feature). You'd get a CORS error.

  A PROXY solves this: instead of the browser calling the backend directly,
  it calls its own server (localhost:5173/api/...) which then silently
  forwards the request to the backend (127.0.0.1:8000/api/...). The browser
  never knows the difference, so no CORS error.

WHAT WAS CHANGED:
  BEFORE:
    export default defineConfig({
      plugins: [react()],
    });

  AFTER:
    export default defineConfig({
      plugins: [react()],
      server: {
        proxy: {
          '/api': {
            target: 'http://127.0.0.1:8000',
            changeOrigin: true,
          }
        }
      }
    });

  This tells Vite: "Any request that starts with /api should be forwarded
  to http://127.0.0.1:8000". So when the frontend calls /api/login, Vite
  sends it to http://127.0.0.1:8000/api/login behind the scenes.

CHANGE 3 — MODIFIED: frontend/src/app/App.jsx
================================================================================

WHY:
  App.jsx was the main file that held all the fake (static) data. It had:
  - A hardcoded list of fake users (initialUsers)
  - A hardcoded list of fake tickets (initialTickets)
  - A hardcoded activity log (initialActivityLog)

  It was also passing this fake data down to every dashboard component.
  The login function just searched through the fake user list instead of
  calling the real backend.

WHAT WAS CHANGED:
  1. REMOVED all fake data arrays (~130 lines of hardcoded mock data).

  2. ADDED: import * as api from '../services/api'
     Now App.jsx can call the real backend through the api.js service.

  3. ADDED: authLoading state
     When the page first loads, the app checks localStorage to see if the
     user was already logged in (from a previous session). While it's
     checking, it shows a loading screen instead of incorrectly redirecting
     to login. This prevents the "flash" where a logged-in user briefly
     sees the login page.

  4. REWROTE handleLogin(identifier, password, setError):
     BEFORE → searched fake user list, compared passwords as plain text
     AFTER  → calls api.login(), gets a real token from the backend,
               stores token + user info in localStorage, goes to dashboard
     If login fails, setError() is called to show an error message.

  5. REWROTE handleRegister(userData, setError):
     BEFORE → just added user to the local fake array
     AFTER  → calls api.register(), saves the returned token and user info

  6. REWROTE handleLogout():
     BEFORE → just cleared local state
     AFTER  → calls api.logout() to tell the backend to delete the token
               (so it can't be reused), then clears localStorage

  7. REMOVED props that were passing fake data to dashboards:
     - tickets, activityLog, users (fake data)
     - onCreateTicket, onUpdateTicket, onUpdateUser (fake handlers)
     Each dashboard now fetches its OWN data directly.

CHANGE 9 — MODIFIED: backend/app/Http/Controllers/Api/AdminUserController.php
================================================================================

WHY:
  The admin's "get all tickets" endpoint (GET /api/admin/demandes) was
  returning tickets WITHOUT the client information attached. So the admin
  dashboard would show tickets but couldn't display the client's name
  or details — it would just show "undefined" or be blank.

  In databases, data is split across multiple tables (tickets in one table,
  clients in another). When you need data from both, you "join" them.
  In Laravel, this is called "eager loading" — you tell it to load the
  related data along with the main data.

WHAT WAS CHANGED:
  BEFORE:
    $demandes = Demande::orderBy('created_at', 'desc')->get();

  AFTER:
    $demandes = Demande::with(['client', 'employee'])
                       ->orderBy('created_at', 'desc')
                       ->get();

  The with(['client', 'employee']) part tells Laravel: "For each ticket,
  also load the client who submitted it AND the employee assigned to it."

  This works because the Demande model has these relationship methods:
    public function client()   { return $this->belongsTo(Client::class, 'id_client'); }
    public function employee() { return $this->belongsTo(Employee::class, 'id_employee'); }

  Without this, the JSON response would be:
    { "id": 1, "titre": "My Issue", "id_client": 5 }

  With eager loading, it becomes:
    { "id": 1, "titre": "My Issue", "id_client": 5,
      "client": { "id": 5, "nom": "Dupont", "mail": "..." } }

CHANGE 10 — MODIFIED: backend/app/Http/Controllers/Api/EmployeeController.php
================================================================================

WHY:
  Same problem as Change 9, but for the employee's ticket list.
  The employee dashboard shows the client's name next to each ticket,
  but the backend wasn't including client data in the response.
  Also, id_client wasn't included in the SELECT query, which is needed
  to display the client ID and to make eager loading work properly.

WHAT WAS CHANGED:
  1. ADDED to both queries (assigned tickets AND new/unassigned tickets):
     ->with('client')
     This loads the client data alongside each ticket.

  2. ADDED 'id_client' to the ->select([...]) list:
     BEFORE: select(['id', 'titre', 'status', 'description', 'priority',
                     'employee_note', 'created_at', 'image'])
     AFTER:  select(['id', 'titre', 'status', 'description', 'priority',
                     'employee_note', 'created_at', 'image', 'id_client'])

     WHY does this matter? Laravel's eager loading needs the foreign key
     column (id_client) to be selected in order to know which client to
     load. If you select specific columns and forget the foreign key,
     the related data won't load — it'll just be null.

HOW EVERYTHING FITS TOGETHER (Summary Flow)
================================================================================

1. User opens the app in their browser (React frontend)

2. App.jsx checks localStorage:
   → If a token is found: restore session, go to dashboard
   → If no token: show Login page

3. User logs in:
   Login.jsx → App.jsx handleLogin → api.js login() →
   POST /api/login → Laravel AuthController →
   checks database → returns token →
   token stored in localStorage → Dashboard shown

4. Dashboard loads:
   e.g. ClientDashboard useEffect → api.js getClientTickets() →
   GET /api/client/tickets (with Bearer token in header) →
   Laravel ClientController (verifies token, finds client) →
   returns client's tickets from database →
   React shows them on screen

5. User submits a ticket:
   Form submit → handleSubmit → api.js createTicket(formData) →
   POST /api/client/tickets (with file if attached) →
   Laravel stores in database → returns new ticket →
   React re-fetches ticket list → new ticket appears

6. Employee resolves a ticket:
   Button click → handleResolve → api.js updateEmployeeTicket() →
   PATCH /api/employee/tickets/123 {status: 'resolved'} →
   Laravel updates ticket in database → ticket disappears from queue

7. User logs out:
   Button click → App.jsx handleLogout → api.js logout() →
   POST /api/logout (backend deletes the token from database) →
   localStorage cleared → Login page shown

================================================================================
IMPORTANT NOTES FOR RUNNING THE PROJECT
================================================================================

1. Start the backend first:
   cd backend
   php artisan serve
   (This starts Laravel at http://127.0.0.1:8000)

2. Then start the frontend:
   cd frontend
   npm run dev
   (This starts React + Vite at http://localhost:5173)

3. Make sure the database is set up:
   cd backend
   php artisan migrate
   (Creates all the tables in the database)

4. Create your first admin account via the database directly or
   by running a seeder:
   php artisan db:seed

5. The frontend auto-proxies all /api calls to the backend,
   so you never need to worry about CORS in development.
